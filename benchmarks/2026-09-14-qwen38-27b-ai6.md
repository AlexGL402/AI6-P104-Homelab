# AI6 — Qwen3.8-27B benchmark (2026-09-14)

## Hardware / software

- Host: AI6
- GPUs: NVIDIA P104-100 8 GB
- Driver: 580.178.04
- CUDA reported by driver: 13.0
- PCIe on AI6: mining-riser setup, effectively x1 links
- Runtime: llama.cpp server
- llama.cpp: `0.4.0-dev`, build 10884, commit `434ddbbc0`
- Model: `unsloth/Qwen3.8-27B-GGUF`
- Quant: `Qwen3.8-27B-UD-Q4_K_M.gguf`
- GGUF file size: 16,464,440,224 bytes (15.33 GiB)
- Split mode: tensor
- Parallel slots: 1

Launch pattern:

```bash
CUDA_VISIBLE_DEVICES=0,1,2 llama-server \
  -m ~/models/qwen38-27b/Qwen3.8-27B-UD-Q4_K_M.gguf \
  -ngl 999 -sm tensor -ts 1,1,1 \
  -c 16384 -np 1 \
  --host 0.0.0.0 --port 8092 --alias qwen38-27b
```

## Benchmark prompt

```text
Write a complete asynchronous HTTP crawler in Python using asyncio and aiohttp. It should support concurrency limits, retries with exponential backoff, per-host rate limiting, URL deduplication, depth limits, robots.txt handling, structured logging, graceful shutdown, and output discovered URLs as JSONL. Explain the architecture briefly, then provide the complete code.
```

OpenAI-compatible chat API, `temperature=0`, `max_tokens=512`.

## 3-GPU VRAM / load snapshot

With Qwen3.8-27B loaded on GPUs 0,1,2:

- VRAM idle after load: about 5.56 / 5.56 / 5.60 GiB
- During generation: about 5.43 / 5.44 / 5.47 GiB shown by host monitor
- GPU load during generation: 96–97%
- Power during generation: ~106 / 113 / 110 W, about 329 W total GPU power
- Temperatures during generation: ~53–55 °C

## 6-GPU VRAM / load snapshot

With Qwen3.8-27B split across all six P104 cards:

- VRAM during generation: about 2.85–2.89 GiB per GPU
- GPU load during generation: 95–96% on all six cards
- Power during generation: ~81.5 / 86.3 / 86.0 / 82.4 / 82.5 / 83.7 W, about 502 W total GPU power
- Temperatures during generation: ~50–53 °C

Despite all six GPUs being heavily utilized, generation throughput is only 12.07 tok/s, slightly slower than the 4-GPU result of 12.32 tok/s. This strongly indicates that the x1-riser topology and synchronization/communication overhead dominate once the model is split across more cards.

## 2-GPU tests

At 16k context, full tensor split across two P104 8 GB cards failed during context initialization:

```text
ggml_backend_cuda_buffer_type_alloc_buffer: allocating 138.02 MiB on device 0: cudaMalloc failed: out of memory
GGML_ASSERT(bufs.back() != nullptr) failed
Aborted (core dumped)
```

At 8k context (`-c 8192`), the same 2×P104 configuration loads successfully and completes the fixed no-thinking benchmark:

```text
prompt eval time = 2432.65 ms / 80 tokens = 32.89 tok/s
eval time        = 44760.91 ms / 512 tokens = 11.42 tok/s
total time       = 47193.56 ms / 592 tokens
```

This is only about 4.0% slower in generation than the 3×P104 16k run (11.42 vs 11.89 tok/s), but the usable context is reduced from 16k to 8k.

## Scaling summary

For the no-thinking runs:

| Configuration | Prompt tok/s | Generation tok/s | Relative gen vs 2× |
|---|---:|---:|---:|
| 2×P104, 8k | 32.89 | 11.42 | 1.00× |
| 3×P104, 16k | 31.16 | 11.89 | 1.04× |
| 4×P104, 16k | 29.60 | 12.32 | 1.08× |
| 6×P104, 16k | 27.49 | 12.07 | 1.06× |

Generation scaling is effectively flat. Four GPUs produced the highest measured generation rate, but only by a small margin. Six GPUs consumed roughly 500 W during generation while performing slightly worse than four GPUs.

## Current conclusion

For AI6's x1-riser topology, **3×P104 is the best practical balance for Qwen3.8-27B UD-Q4_K_M at 16k context**, while **4×P104 is the absolute fastest measured configuration** in this test at 12.32 tok/s. The difference between 3 and 4 GPUs is only ~3.6%, so the extra card is usually better reserved for another worker.

Two P104 cards are surprisingly viable if 8k context is enough: generation is 11.42 tok/s, very close to the 3-GPU result, and this leaves four GPUs available for other workers. Two cards do not fit the tested 16k full-offload configuration.

Using all six P104 cards for one Qwen3.8 instance is inefficient on AI6: throughput does not improve, prompt processing gets slower, and total GPU power rises to about 500 W. The better architecture is multiple independent workers rather than one 6-GPU tensor-parallel model.

Thinking control works correctly through the chat request:

```json
"chat_template_kwargs": {"enable_thinking": false}
```

Disabling thinking does not materially change raw token generation speed; it changes where the generated token budget is spent. With thinking enabled, the first 512-token run was entirely `reasoning_content`; with thinking disabled, the answer was emitted directly as normal `content`.

## Recommended next tests

1. **3×P104 context scaling:** repeat the same fixed no-thinking benchmark at 4k, 8k, 16k and 32k context (32k only if it fits). This isolates the cost of KV/context growth on the practical 3-GPU configuration.
2. **Long-prompt / prefill test:** use a fixed ~8k-token prompt and generate 128 tokens. The short 80-token prompt above is useful for generation throughput but does not expose PCIe x1 prefill penalties strongly enough.
3. **3+3 parallel throughput:** run two independent Qwen3.8 workers on GPUs 0-2 and 3-5 simultaneously, send the same request to both, and measure aggregate generation tok/s plus wall power. This directly tests the proposed production architecture.
4. **2+2+2 parallel throughput:** if 8k context is acceptable, run three independent 2-GPU Qwen3.8 workers and measure aggregate throughput. Based on the single-worker 2-GPU result, this may maximize total tokens/s per AI6 host.
5. **Power-limit efficiency:** benchmark the chosen 3-GPU worker at 120 W, 140 W, 160 W and 180 W per card. Record tok/s, total GPU watts and tok/s per watt.
6. **Reasoning-budget test:** use the same coding task with thinking OFF and with controlled reasoning budgets (for example 256, 512, 1024 generated reasoning tokens) and compare answer quality, latency and token cost.
7. **Agent workload test:** run Pi/Coding Agent against a real repository task rather than a synthetic prompt. Record time-to-completion, number of tool calls, tokens, compile/test success and whether human correction was required.
8. **T5600 PCIe comparison:** when the Dell T5600 is ready, repeat the exact same Qwen3.8 benchmark on 2 or 3 P104 cards in direct PCIe slots. This will quantify the real x1-riser penalty versus wider links.

For the next immediate test, **3+3 parallel Qwen3.8 throughput** is the most useful because it directly validates the intended AI6 deployment model.
