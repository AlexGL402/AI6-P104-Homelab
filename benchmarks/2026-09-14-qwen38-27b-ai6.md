# AI6 — Qwen3.8-27B benchmark (2026-09-14)

## Hardware / software

- Host: AI6
- GPUs: NVIDIA P104-100 8 GB
- Driver: 580.178.04
- CUDA reported by driver: 13.0
- PCIe on AI6: mining-riser setup, effectively x1 links
- Runtime: llama.cpp server
- llama.cpp: `0.4.0-dev`, build 10884, commit `434ddbbc0`
- Model: `unsloth/Qwen3.8-27B-GGUF`
- Quant: `Qwen3.8-27B-UD-Q4_K_M.gguf`
- GGUF file size: 16,464,440,224 bytes (15.33 GiB)
- Split mode: tensor
- Parallel slots: 1

Launch pattern:

```bash
CUDA_VISIBLE_DEVICES=0,1,2 llama-server \
  -m ~/models/qwen38-27b/Qwen3.8-27B-UD-Q4_K_M.gguf \
  -ngl 999 -sm tensor -ts 1,1,1 \
  -c 16384 -np 1 \
  --host 0.0.0.0 --port 8092 --alias qwen38-27b
```

## Benchmark prompt

```text
Write a complete asynchronous HTTP crawler in Python using asyncio and aiohttp. It should support concurrency limits, retries with exponential backoff, per-host rate limiting, URL deduplication, depth limits, robots.txt handling, structured logging, graceful shutdown, and output discovered URLs as JSONL. Explain the architecture briefly, then provide the complete code.
```

OpenAI-compatible chat API, `temperature=0`, `max_tokens=512`.

## 3-GPU VRAM / load snapshot

- GPU load during generation: 96–97%
- Power during generation: ~106 / 113 / 110 W, about 329 W total GPU power

## 6-GPU single-worker snapshot

With Qwen3.8-27B split across all six P104 cards:

- VRAM during generation: about 2.85–2.89 GiB per GPU
- GPU load during generation: 95–96% on all six cards
- Power during generation: ~81.5 / 86.3 / 86.0 / 82.4 / 82.5 / 83.7 W, about 502 W total GPU power
- Temperatures during generation: ~50–53 °C

Despite all six GPUs being heavily utilized, generation throughput is only 12.07 tok/s, slightly slower than the 4-GPU result of 12.32 tok/s. This strongly indicates that the x1-riser topology and synchronization/communication overhead dominate once the model is split across more cards.

## 2-GPU tests

At 16k context, full tensor split across two P104 8 GB cards failed during context initialization:

```text
ggml_backend_cuda_buffer_type_alloc_buffer: allocating 138.02 MiB on device 0: cudaMalloc failed: out of memory
GGML_ASSERT(bufs.back() != nullptr) failed
Aborted (core dumped)
```

At 8k context (`-c 8192`), the same 2×P104 configuration loads successfully and completes the fixed no-thinking benchmark:

```text
prompt eval time = 2432.65 ms / 80 tokens = 32.89 tok/s
eval time        = 44760.91 ms / 512 tokens = 11.42 tok/s
total time       = 47193.56 ms / 592 tokens
```

This is only about 4.0% slower in generation than the 3×P104 16k run (11.42 vs 11.89 tok/s), but the usable context is reduced from 16k to 8k.

## Parallel 3+3 throughput

Two independent Qwen3.8 workers were started simultaneously:

- worker A: GPUs 0,1,2, `-c 16384`, port 8092
- worker B: GPUs 3,4,5, `-c 16384`, port 8093
- same fixed prompt, thinking OFF, 512 output tokens each

Observed result:

| Worker | Prompt tok/s | Generation tok/s | Generated tokens | Total time |
|---|---:|---:|---:|---:|
| A (0,1,2) | 30.97 | 12.07 | 512 | 44.92 s |
| B (3,4,5) | 31.08 | 12.00 | 512 | 45.15 s |
| **Aggregate** | — | **24.07 tok/s** | 1024 | **45.45 s wall** |

During the parallel run all six GPUs were loaded around 96–97%, with roughly 5.43–5.47 GiB VRAM used per GPU. A representative power snapshot was approximately 110 / 114 / 114 / 107 / 108 / 110 W, or about 663 W total GPU power.

This validates the 3+3 production architecture: compared with one 6-GPU Qwen3.8 instance at 12.07 tok/s, two 3-GPU workers deliver **24.07 tok/s aggregate**, essentially doubling useful host throughput while preserving 16k context per worker. Per-worker speed remains almost unchanged from the isolated 3-GPU benchmark, so the two workers do not materially interfere with each other.

## Parallel 2+2+2 throughput

Three independent Qwen3.8 workers were started simultaneously, each at 8k context:

- worker 01: GPUs 0,1, `-c 8192`, port 8094
- worker 23: GPUs 2,3, `-c 8192`, port 8092
- worker 45: GPUs 4,5, `-c 8192`, port 8093
- same fixed prompt, thinking OFF, 512 output tokens each

Observed result:

| Worker | Prompt tok/s | Generation tok/s | Generated tokens | Total time |
|---|---:|---:|---:|---:|
| 01 (0,1) | 32.42 | 11.58 | 512 | 46.58 s |
| 23 (2,3) | 21.17 | 11.57 | 512 | 47.95 s |
| 45 (4,5) | 21.12 | 11.58 | 512 | 47.93 s |
| **Aggregate** | — | **34.73 tok/s** | 1536 | **48.30 s wall** |

During generation all six GPUs were at about 97% load. VRAM use was about **7.77 GiB / 8.00 GiB per GPU**, leaving very little headroom. A representative power snapshot was approximately 133.6 / 138.2 / 132.5 / 131.5 / 138.7 / 135.0 W, or about **809 W total GPU power**. Temperatures were about 57–61 °C with fans around 65–70%.

Compared with the 3+3 layout, 2+2+2 improves aggregate generation throughput from 24.07 to **34.73 tok/s**, a gain of about **44%**, at the cost of reducing context from 16k to 8k per worker and using substantially more GPU power. Compared with one 6-GPU tensor-parallel worker at 12.07 tok/s, the 2+2+2 layout delivers about **2.88×** as much aggregate generation throughput.

The three workers maintain almost identical generation speed (~11.57–11.58 tok/s), which shows that concurrent decoding scales very well across independent GPU pairs. Prompt throughput is less uniform: worker 01 reached 32.42 tok/s while workers 23 and 45 were around 21.1 tok/s. This should be investigated with a repeated run and a longer-prompt prefill test, but it did not materially affect generation throughput.

## Host throughput comparison

| Layout | Workers | Context / worker | Aggregate gen tok/s | Representative GPU power | Main trade-off |
|---|---:|---:|---:|---:|---|
| 6-way tensor parallel | 1 | 16k | 12.07 | ~502 W | Lowest throughput; inefficient scaling |
| 3+3 | 2 | 16k | 24.07 | ~663 W | Best balance for 16k context |
| 2+2+2 | 3 | 8k | **34.73** | ~809 W | Maximum measured host throughput; very tight VRAM |

## Current conclusion

For AI6's x1-riser topology, **3×P104 is the best practical balance for one Qwen3.8-27B UD-Q4_K_M worker at 16k context**, while **4×P104 is the absolute fastest measured single-worker configuration** in this test at 12.32 tok/s. The difference between 3 and 4 GPUs is only ~3.6%, so the extra card is usually better reserved for another worker.

For multi-worker deployment, there are now two useful operating modes:

- **3+3 at 16k:** 24.07 tok/s aggregate, substantially more VRAM headroom, and lower total GPU power.
- **2+2+2 at 8k:** **34.73 tok/s aggregate**, the highest measured AI6 host throughput, but VRAM is nearly full at ~7.77 GiB per GPU and GPU power rises to roughly 809 W.

One model spread across all six GPUs should be avoided for this workload. Independent workers make much better use of the P104 farm.

Thinking control works correctly through the chat request:

```json
"chat_template_kwargs": {"enable_thinking": false}
```

Disabling thinking does not materially change raw token generation speed; it changes where the generated token budget is spent. With thinking enabled, the first 512-token run was entirely `reasoning_content`; with thinking disabled, the answer was emitted directly as normal `content`.

## Recommended next tests

1. **Repeat 2+2+2 once:** verify the unusually low prompt throughput on workers 23 and 45 and confirm the 34.7 tok/s aggregate generation result.
2. **Long-prompt / prefill test:** use a fixed ~8k-token prompt and generate 128 tokens. This should expose the PCIe x1 prefill penalty much more clearly.
3. **Power-limit efficiency:** test 2+2+2 and/or 3+3 at lower power limits to find the best tok/s/W point; 2+2+2 currently draws around 809 W GPU-only in the observed snapshot.
4. **3×P104 context scaling:** repeat at 4k, 8k, 16k and 32k context (32k only if it fits) to quantify KV/cache cost.
5. **Reasoning-budget test:** compare thinking OFF with controlled reasoning budgets and record latency, token count and answer quality.
6. **Agent workload test:** run Pi/Coding Agent against a real repository task and record tool calls, completion time, compile/test success and human corrections.
7. **T5600 PCIe comparison:** repeat the exact benchmark on direct PCIe slots to quantify the x1-riser penalty.

## 2026-09-22 follow-up — 2× CMP 50HX

The same Qwen3.8-27B GGUF was retested after replacing the P104 setup with two NVIDIA CMP 50HX 10 GB cards.

### Hardware / topology

- GPUs: 2× NVIDIA CMP 50HX, 10 GiB each
- Driver / KMD: 610.43.03
- CUDA UMD reported by `nvidia-smi`: 13.3
- GPU0: PCIe Gen1 x4 (`0000:01:00.0`)
- GPU1: PCIe Gen1 x1 (`0000:02:00.0`, mining-style riser)
- `nvidia-smi topo -m`: GPU0 ↔ GPU1 = `PHB`
- Power limit: 184 W per GPU
- Runtime/model/quant: same llama.cpp build and `Qwen3.8-27B-UD-Q4_K_M.gguf`

Launch command:

```bash
CUDA_VISIBLE_DEVICES=0,1 \
~/llama.cpp/build/bin/llama-server \
  -m ~/models/qwen38-27b/Qwen3.8-27B-UD-Q4_K_M.gguf \
  -ngl 999 \
  -sm tensor \
  -ts 1,1 \
  -c 16384 \
  -np 1 \
  --host 0.0.0.0 \
  --port 8092 \
  --alias qwen38-27b
```

The 16k configuration loaded successfully with full GPU offload. Idle VRAM after load was about **8319 MiB per GPU**, so unlike 2×P104 8 GB, the two CMP 50HX cards can run this model at 16k context without the previous CUDA-buffer OOM.

### Fixed 512-token run

Same crawler prompt, `temperature=0`, `max_tokens=512`. The server's default reasoning-preserve behavior was enabled, so the 512 generated tokens were emitted as `reasoning_content`, matching the earlier style of the thinking-enabled P104 run.

```text
prompt eval time = 18346.82 ms / 120 tokens = 6.54 tok/s
eval time        = 27420.31 ms / 512 tokens = 18.64 tok/s
total time       = 45767.14 ms / 632 tokens
```

| Configuration | Context | Thinking | Prompt tok/s | Generation tok/s | 512-token eval | Total |
|---|---:|:---:|---:|---:|---:|---:|
| 3×P104 | 16k | ON | 28.75 | 11.94 | 42.81 s | 46.99 s |
| **2×CMP 50HX (x4+x1)** | **16k** | **ON/default** | **6.54** | **18.64** | **27.42 s** | **45.77 s** |

Generation throughput is about **56% higher than the 3×P104 16k thinking-enabled run** (18.64 vs 11.94 tok/s). It is also about **63% higher than the 2×P104 8k result** (18.64 vs 11.42 tok/s), although the latter used thinking OFF and a smaller context setting.

Prompt/prefill throughput is much lower on the CMP pair in this run: **6.54 tok/s** versus roughly 29–33 tok/s in the earlier P104 measurements. Because the new topology is asymmetric (Gen1 x4 + Gen1 x1) and tensor-split decoding requires both GPUs, PCIe/synchronization overhead is a likely contributor; this needs a dedicated repeated long-prompt test before attributing the full difference to PCIe alone.

### Load / power snapshot

During generation:

- GPU0 load: ~93%
- GPU1 load: ~96%
- GPU0 power: ~149.4 W
- GPU1 power: ~162.9 W
- Total GPU power: ~312.3 W
- VRAM: ~8.22 GiB / 10 GiB per GPU
- Temperatures: ~46 °C / 49 °C
- Fans: ~35% / 38%

This gives roughly **0.0597 generation tok/s per GPU watt** for the observed snapshot (18.64 tok/s / 312.3 W).

### Preliminary CMP 50HX conclusion

For this single-worker Qwen3.8-27B test, **2×CMP 50HX is substantially faster at generation than the older 2–4×P104 configurations and can hold 16k context on only two cards**. The main unresolved issue is prompt/prefill performance on the asymmetric Gen1 x4 + x1 tensor-split topology.

Next useful checks:

1. Repeat the exact run with `chat_template_kwargs.enable_thinking=false` for a direct OFF-vs-OFF comparison.
2. Repeat the fixed request several times to separate first-run/cache/graph effects from steady-state performance.
3. Test a long prompt with a short output to isolate prefill throughput.
4. Compare tensor split modes / placement if supported by the current llama.cpp build.
5. If a wider PCIe path becomes available for GPU1, repeat the same benchmark unchanged to quantify the x1 penalty.
