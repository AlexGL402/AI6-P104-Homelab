# AI6 — Qwen3.8-27B benchmark (2026-09-14)

## Hardware / software

- Host: AI6
- GPUs: NVIDIA P104-100 8 GB
- Driver: 580.178.04
- CUDA reported by driver: 13.0
- PCIe on AI6: mining-riser setup, effectively x1 links
- Runtime: llama.cpp server
- llama.cpp: `0.4.0-dev`, build 10884, commit `434ddbbc0`
- Model: `unsloth/Qwen3.8-27B-GGUF`
- Quant: `Qwen3.8-27B-UD-Q4_K_M.gguf`
- GGUF file size: 16,464,440,224 bytes (15.33 GiB)
- Split mode: tensor
- Parallel slots: 1

Launch pattern:

```bash
CUDA_VISIBLE_DEVICES=0,1,2 llama-server \
  -m ~/models/qwen38-27b/Qwen3.8-27B-UD-Q4_K_M.gguf \
  -ngl 999 -sm tensor -ts 1,1,1 \
  -c 16384 -np 1 \
  --host 0.0.0.0 --port 8092 --alias qwen38-27b
```

## Benchmark prompt

```text

It should support concurrency limits, retries with exponential backoff, per-host rate limiting, URL deduplication, depth limits, robots.txt handling, structured logging, graceful shutdown, and output discovered URLs as JSONL. OpenAI-compatible chat API, `temperature=0`, `max_tokens=512`.

## 2-GPU tests

At 16k context, full tensor split across two P104 8 GB cards failed during context initialization:

```text
ggml_backend_cuda_buffer_type_alloc_buffer: allocating 138.02 MiB on device 0: cudaMalloc failed: out of memory
GGML_ASSERT(bufs.back() != nullptr) failed
Aborted (core dumped)
```

At 8k context (`-c 8192`), the same 2×P104 configuration **loads successfully** and reaches:

```text
model loaded
listening on http://0.0.0.0:8092
n_ctx_slot = 8192
```

No throughput benchmark has been recorded yet for the 2-GPU 8k run because the server was stopped before the test request.

## Current conclusion

For AI6's x1-riser topology, **3×P104 is currently the practical sweet spot for Qwen3.8-27B UD-Q4_K_M at 16k context**. Moving from 3 to 4 GPUs improves generation only from 11.89 to 12.32 tok/s (~3.6%), while prompt throughput actually drops slightly (31.16 → 29.60 tok/s).

Two P104 cards are enough to load the model at 8k context, but not at 16k with the tested full-offload tensor-split settings.

Thinking control works correctly through the chat request:

```json
"chat_template_kwargs": {"enable_thinking": false}
```

Disabling thinking does not materially change raw token generation speed; it changes where the generated token budget is spent. With thinking enabled, the first 512-token run was entirely `reasoning_content`; with thinking disabled, the answer was emitted directly as normal `content`.
