# J1900 + P104-100 mini-node benchmark and setup notes (2026-09-27)

## Goal

Build a low-power always-on Home Lab / local-AI node around the J1900 mini board and one NVIDIA P104-100 8 GB.

## Hardware / platform

- Host: J1900 mini board / Ubuntu 24.04
- CPU: Intel Celeron J1900 / Bay Trail
- RAM: 8 GB
- GPU: NVIDIA P104-100 8 GB (GP104, compute capability 6.1)
- GPU PCI bus: 0000:02:00.0
- NVIDIA driver: 555.42.06 proprietary
- CUDA reported by nvidia-smi: 12.5
- Ollama working version for this driver/GPU combination: 0.24.0
- Ollama context used for the saved tests: 4096
- GPU power limit during the saved tests: 180 W

## BIOS / POST findings

The P104 initially caused POST / resource-allocation problems on this board.

The working BIOS change was:

```text
Max TOLUD = 2 GB
```

With Max TOLUD at 2 GB, the P104 passes POST and Ubuntu boots.

Important:
- Keep Max TOLUD at 2 GB on this configuration.
- Setting CSM Video to "Do not launch" caused a black screen and should not be used here.
- PCIe Gen1 was used during troubleshooting, but the present endpoint capability and upstream-port capability are shown below.

## Current PCIe topology

```text
-[0000:00]-+-1c.0-[01]----00.0  Realtek RTL8111/8168/8211/8411
           \-1c.2-[02]----00.0  NVIDIA GP104 [P104-100]
```

Current upstream root-port capabilities:

```text
00:1c.0
  LnkCap: Speed 5GT/s, Width x1
  LnkSta: Speed 2.5GT/s, Width x1

00:1c.2
  LnkCap: Speed 5GT/s, Width x1
  LnkSta: Speed 2.5GT/s, Width x1
```

Current P104 endpoint:

```text
LnkCap: Speed 2.5GT/s, Width x4
LnkSta: Speed 2.5GT/s, Width x1 (downgraded)
```

So the P104 itself advertises Gen1 x4, but on the current J1900 root-port path it negotiates Gen1 x1.

A prior CMP40 run on this mini platform was observed at x4, but the exact upstream root-port dump from that specific run was not saved. Do not treat today's x1 root-port layout as proof that x4 is impossible on every configuration of the board; the exact lane-routing / BIOS state remains unresolved.

## NVIDIA driver transition

The machine previously contained the CMP-oriented 610 Open Kernel Module setup.

P104 failed under that stack because the Open NVIDIA module rejected the Pascal P104 path due to lack of GSP support.

The final working P104 stack is:

```text
NVIDIA driver: 555.42.06
Kernel module license: NVIDIA
Kernel driver in use: nvidia
GPU visible in nvidia-smi: yes
VRAM: 8192 MiB
```

Do not re-introduce the old `forge-cmp` 610.43.03 Open module stack on this P104 host.

## Ollama compatibility finding

Recent Ollama builds tested on this host rejected the P104 with driver 555:

```text
device="NVIDIA P104-100"
compute=6.1
driver=555
required_driver="570 or newer"
```

Observed behavior:

| Ollama version | Result |
|---|---|
| 0.33.3 | GPU rejected; CPU fallback |
| 0.30.6 | GPU rejected; CPU fallback |
| 0.24.0 | CUDA GPU detected and used |

Working 0.24.0 discovery:

```text
library=CUDA
compute=6.1
description="NVIDIA P104-100"
libdirs=ollama,cuda_v12
driver=12.5
total="8.0 GiB"
available="7.9 GiB"
```

The 0.30.6 CPU fallback also exposed a RAM issue at context 32768: the Qwen3 4B model allocated a ~4.5 GiB CPU KV cache and the service was killed by the Linux OOM killer. The stable service context was therefore returned to 4096.

## Ollama service settings

Recommended always-on mini-node settings:

```ini
[Service]
Environment="OLLAMA_MODELS=/var/lib/ollama-models"
Environment="OLLAMA_CONTEXT_LENGTH=4096"
Environment="OLLAMA_KEEP_ALIVE=24h"
Environment="OLLAMA_VULKAN=0"
Environment="GGML_VK_VISIBLE_DEVICES=-1"
```

The long keep-alive is especially useful on the current Gen1 x1 PCIe link: pay the model-load cost once, then keep the main model resident in VRAM.

## 4B vs 8B practical comparison

| Model | Prompt tok/s | Generation tok/s | Total time | Approx. VRAM |
|---|---:|---:|---:|---:|
| Qwen3 4B | 475.15 | 37.31 | 15.573 s | ~3.08 GiB |
| Qwen3 8B | 294.21 | 26.92 | 20.957 s | ~5.3-5.45 GiB |

The 8B decode rate is about 27.8% lower than the 4B result, but ~26.9 tok/s remains comfortably interactive.

Practical role split for the mini node:

- Qwen3 8B: primary Home Lab assistant for Linux, configs, code, Docker, networking, diagnostics and more complex requests.
- Qwen3 4B: fast lightweight model for routing, automation, short commands and simple agent work.

## Mini-node operating conclusion

The J1900 + P104 combination is viable as an economical always-on local-AI / Home Lab node if the main model remains resident in VRAM.

Recommended use:

- Keep Qwen3 8B loaded for higher-quality interactive work.
- Keep Qwen3 4B available as a faster lightweight fallback.
- Use 4096 context as the current safe baseline on an 8 GB system.
- Keep the model resident for long periods to avoid repeated cold-load transfers over Gen1 x1.
- Treat x4 lane recovery as an optimization project, not a blocker for fully GPU-resident 4B/8B inference.

Potential additional low-CPU services for the node include DNS/ad blocking, WireGuard/Tailscale, reverse proxy, monitoring, MQTT, Node-RED, lightweight Git hosting, Syncthing and local API routing to larger AI hosts.
