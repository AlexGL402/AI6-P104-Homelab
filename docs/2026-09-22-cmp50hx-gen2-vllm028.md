
### Old forge initramfs hook conflict

The old hook failed because the installer moved the forge-cmp module away:

```text
/etc/initramfs-tools/hooks/forge-cmp
```

It was renamed and made non-executable:

```bash
sudo mv /etc/initramfs-tools/hooks/forge-cmp \
        /etc/initramfs-tools/hooks/forge-cmp.disabled
sudo chmod -x /etc/initramfs-tools/hooks/forge-cmp.disabled
sudo update-initramfs -u -k $(uname -r)
```

### Gen2 service

Installed manually after the first installer run stopped at initramfs:

```bash
sudo install -m 0755 /opt/cmp50hx-unlock/cmp50hx/cmp50hx-gen2.sh \
  /usr/local/sbin/cmp50hx-gen2

sudo install -m 0644 /opt/cmp50hx-unlock/cmp50hx/cmp50hx-gen2.service \
  /etc/systemd/system/cmp50hx-gen2.service

sudo systemctl daemon-reload
sudo systemctl enable cmp50hx-gen2.service
```

After reboot, verified:

```bash
modinfo -n nvidia
nvidia-smi --query-gpu=index,pcie.link.gen.current,pcie.link.width.current,pcie.link.gen.max,pcie.link.width.max --format=csv
```

Working result:

```text
/lib/modules/6.8.0-139-generic/updates/nvidia.ko

index, pcie.link.gen.current, pcie.link.width.current, pcie.link.gen.max, pcie.link.width.max
0, 2, 4, 2, 16
1, 2, 1, 2, 16
```

So:

- GPU0: PCIe Gen2 x4
- GPU1: PCIe Gen2 x1
- both cards advertise max Gen2 x16
- before this change they were Gen1 x4 and Gen1 x1

Useful verification:

```bash
journalctl -u cmp50hx-gen2.service -b --no-pager
sudo dmesg | grep -E 'CMP50_GEN2|CMP50_STOCKFLOW|CMP50_REBAR' | tail -100
```

- Current link: PCIe Gen1 x4
- Reported max width: x16
- Reported max generation in the current endpoint state: Gen1
- NVIDIA driver/KMD: 610.43.03

`nvidia-smi`:


Direct pinned-memory PCIe bandwidth using the same PyTorch methodology as the CMP40 validation:

| Transfer size | H2D | D2H |
|---:|---:|---:|
| 256 MiB | 0.79 GB/s | 0.84 GB/s |
| 512 MiB | 0.79 GB/s | 0.84 GB/s |
| 1024 MiB | 0.79 GB/s | 0.84 GB/s |

This is the pre-hardware-mod CMP50 baseline for future x4 -> x16 comparison on the X99 platform.

The card is currently back in the Gen1 endpoint-advertising state. Earlier, with the `xrip/cmp50hx-unlock` Gen2 patch/service active, the same CMP50 class successfully advertised and operated at Gen2. Therefore the present Gen1 result does not imply a Gen1-only hardware limitation; the Gen2 unlock path is simply not active in this host state.

The curve flattens sharply above 180 W: 47.5 t/s at 180 W, 48.3 t/s at 190 W, and 48.5 t/s at max PL. For this workload, 170 W is the efficiency-oriented setting while 180 W is a practical performance sweet spot.
