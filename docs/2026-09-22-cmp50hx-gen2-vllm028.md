## Practical recommendations from the T5600 CMP50 tests

### Power limit

- **170 W**: efficiency-oriented setting. Qwen3-14B delivered 46.2 t/s in the clean sweep.
- **180 W**: recommended performance setting. Qwen3-14B delivered 47.5 t/s and the standardized multi-model tests remained cool and stable.
- **190 W**: only a small additional gain (48.3 t/s Qwen3) for noticeably higher board power.
- **225 W / max**: not useful for this workload; the card drew ~192 W and Qwen3 only reached 48.5 t/s.

For day-to-day LLM inference on this CMP50, **180 W is the practical performance sweet spot**; use 170 W when efficiency/noise matters more.

### Model choice by measured behavior

- **Highest measured raw throughput:** Mistral Nemo 12B Q4_K_M. Best `llama-bench` result: 57.02 t/s generation and 1332.73 t/s pp512.
- **Best measured long-context VRAM behavior:** Gemma 3 12B Q4_K_M. It completed 32K context on one 10 GB CMP50 with full GPU offload and no generation-speed loss in the tested prompt, but 32K leaves essentially no VRAM safety margin.
- **Practical long-context default:** Gemma 3 at 16K is the safer measured configuration, with 8755 MiB VRAM used. A 24K setting is a reasonable next test if a middle ground between 16K safety and 32K maximum is desired; 24K has not yet been measured.
- **14B option:** Qwen3-14B Q4_K_M is a good throughput baseline among the tested 14B models and beat Phi-4 in generation while using less VRAM in the standardized run.
- **Coding-specific model:** Qwen2.5-Coder-14B Q4_K_M remains available and measured at 45.2 t/s at 170 W in the manual test. No standardized `llama-bench` run has been recorded for it yet.
- **Phi-4:** usable and stable, but in these measurements it offered lower generation throughput and higher VRAM use than Qwen3-14B. This is not a statement about answer quality.

### PCIe / host conclusion

The T5600 CMP50 is operating at PCIe Gen2 x4 and measured 1.51 GB/s H2D / 1.56 GB/s D2H. The compute and llama.cpp results above show the card is functioning normally in this configuration. The current tests do not establish how much these single-GPU llama.cpp workloads would improve with a wider PCIe link; a width comparison would require controlled measurements on the same card/model/settings.

## 2026-09-26 — T5600 CMP50 recovery after power disturbance

After a mains/power disturbance, the CMP50 remained visible on PCIe at `03:00.0`, and the Gen2 service could still train the link, but NVIDIA GSP initialization repeatedly failed with:

```text
CMP50_STOCKFLOW_V551: SIGNED_EXACT_STATE_MISMATCH
CMP50_COMPUTE_UNLOCK_V274: POST_FWSEC_COMMIT_FAIL
Max GSP-RM boot attempts exceeded: 4/4
RmInitAdapter: Cannot initialize GSP firmware RM
```

Reloading the NVIDIA kernel modules did not recover the card.

A one-shot UEFI pre-OS unlock was then tested. The stock Linux EFI build from `xrip/cmp50hx-unlock` stopped during its optional BAR0 VBIOS dump on this Dell T5600:

```text
[vbios] dump 1MB from BAR0+0x11000 ...
```

Rebuilding `efi-unlock/50HXUNLK.EFI` without `-DVBIOS_DUMP` allowed the UEFI path to proceed and the GPU initialized successfully on the next BootNext cycle.

Working local change in `efi-unlock/build.sh`:

```diff
-    -DDIRECT_SEC2 -DRELEASE_BUILD -DVBIOS_DUMP \
+    -DDIRECT_SEC2 -DRELEASE_BUILD \
```

Successful post-boot state:

```text
GPU:       NVIDIA CMP 50HX
VRAM:      10240 MiB
PCIe:      Gen2 x4
GSP:       ready
SS0/SS1:   0x88888888 / 0x8
Xid:       none observed
RmInit:    successful
```

Relevant successful driver markers included:

```text
FWSEC_COMPLETE_GSP_UNTOUCHED
POST_FWSEC_PRE_GSP_HANDOFF_PASS
SIGNED_FULLSPEED_STOCK_RELOCK_WPR_DOWN_PASS
FULLSPEED_STOCK_RELOCK_WPR_DOWN_HANDOFF_PASS
CMP50_GSP_READY_V551
```

The driver-side immediate retrain still logged one `CMP50_GEN2: RETRAIN_FAIL`, but the card ultimately reported an active Gen2 x4 link, so the final link state was healthy.

Practical recovery note for this T5600: keep a tested UEFI unlock binary built without `VBIOS_DUMP`; use a one-shot `BootNext` test before making any boot-order change permanent.

Reducing context to 2048 allowed one more GPU layer:

```text
-ngl:       28
context:    2048
```

This is effectively at the VRAM ceiling.

### Scaling summary

| Mode | VRAM | Prompt | Generation | Result |
|---|---:|---:|---:|---|
| 26 layers / ctx 4096 | 9307 MiB | 15.7 t/s | 5.9 t/s | works |
| 27 layers / ctx 4096 | 9623 MiB | 17.2 t/s | 6.3 t/s | works; highest tested at 4K |
| 28 layers / ctx 4096 | — | — | — | OOM on ~261 MiB compute buffer |
| 28 layers / ctx 2048 | 9775 MiB | 17.9 t/s | 6.6 t/s | works; essentially no VRAM headroom |
| 35 layers / ctx 4096 | — | — | — | OOM; attempted ~11.3 GiB CUDA allocation |

The extra layer from 27 -> 28 at reduced context improved generation only from 6.3 to 6.6 t/s (~4.8%) and prompt processing from 17.2 to 17.9 t/s (~4.1%).

### Practical conclusion

The 24B Q4_K_M model is technically usable on one CMP50 10 GB with CPU offload, but it is not an attractive interactive configuration on this T5600:

- GPU utilization is only around 11–14% in the observed hybrid runs.
- Generation is around 6 t/s, far below the fully GPU-resident 12–14B models tested on the same card.
- The 28-layer / 2K mode leaves almost no VRAM safety margin.
- The more practical 4K context setting is `-ngl 27`, but throughput is still only 6.3 t/s.

For day-to-day use on one CMP50 10 GB, the fully GPU-resident 12–14B Q4 models remain the better fit. The 24B result is useful as an upper-bound hybrid/offload experiment, not as the preferred agent/inference configuration.


## 2026-09-26 — Mistral Small 24B IQ3_XS on one CMP50

Model:

- `Mistral-Small-24B-Instruct-2501-IQ3_XS.gguf`
- file size on disk: ~9.3 GiB
- one CMP 50HX 10 GB
- context: 4096
- PL target: 180 W
- same coding prompt used in the earlier 24B comparison

### Full offload attempt

`-ngl 99 -c 4096` failed during context creation because there was not enough VRAM left for the KV cache:

```text
allocating 640.00 MiB on device 0
cudaMalloc failed: out of memory
failed to allocate buffer for kv cache
```

This shows that the IQ3_XS weights are small enough to get very close to full residency, but a 4K context still needs additional VRAM for KV/cache and runtime buffers.

### Working point

`-ngl 35 -c 4096` succeeded.

Observed GPU telemetry:

```text
VRAM:       8835 MiB
GPU util:     28%
GPU power: 132.16 W
Temp:          49 C
Core:        2085 MHz
Memory:      7500 MHz
Prompt:        13.8 t/s
Generation:     9.1 t/s
```

Compared with the earlier Q4_K_M hybrid result at 4K:

- Q4_K_M, `-ngl 27`: 6.3 t/s generation
- IQ3_XS, `-ngl 35`: 9.1 t/s generation

That is about a 44% generation-throughput improvement for IQ3_XS in this test.

### Higher layer-count attempts

`-ngl 40 -c 4096` failed while allocating the CUDA model buffer:

```text
allocating 8938.38 MiB on device 0
cudaMalloc failed: out of memory
failed to allocate CUDA0 buffer of size 9372569600
```

`-ngl 37 -c 4096` also failed during model loading:

```text
allocating 8256.58 MiB on device 0
cudaMalloc failed: out of memory
failed to allocate CUDA0 buffer of size 8657653760
```

Therefore the tested working ceiling is currently `-ngl 35`; `-ngl 36` has not yet been tested, while 37 and 40 are confirmed OOM at 4K.

### Current takeaway

IQ3_XS is substantially more practical than Q4_K_M for this 24B model on a single 10 GB CMP50 because more layers can stay on GPU. The measured generation rate improved from ~6.3 t/s to 9.1 t/s at 4K context.

A second GPU is the next logical experiment. A second CMP50 would provide 20 GB total VRAM and should allow the model to be distributed across two GPUs with much less CPU offload. A CMP40 as the second card is also worth testing as a mixed-GPU configuration, especially to measure whether the slower/older card and riser bandwidth reduce decode performance enough to offset the extra VRAM.
